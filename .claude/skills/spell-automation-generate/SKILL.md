# Spell Automation Generation

Turn proposals from a `spell-automation-proposals.md` report (produced by the `spell-automation-triage` skill) into working automation code for the fantik-automations Foundry VTT module. Each spell is implemented by its own Opus agent; the orchestrator wires registration and verifies the result.

**Every generated automation is marked as autogenerated** — a banner comment in the file plus an `autogenerated: true` field in the definition — so manually written and generated code stay distinguishable. Marker format, degradation rules, and code conventions live in `references/generation-conventions.md`; generator agents must read it.

**Scope default: generate ALL proposals in the report, degraded where blocked.** Proposals with feasibility `needs-new-event` or `needs-gm-or-rights` are still generated: the parts current framework events support are implemented, the rest degrades to visible marker effects or is skipped — never chat reminder cards. The module's hard rule applies throughout: never block or cancel a player's vanilla cast or roll.

## Inputs

- A proposals report. Default: `spell-automation-proposals.md` in the module root; accept a user-specified path.
- Optionally, a user-given subset of spell names to generate. Without one, generate every proposal in the report.

## Workflow

### Step 1: Parse the report

```bash
node "<skill-dir>/scripts/parse_proposals.mjs" spell-automation-proposals.md --out proposals-worklist.json
```

The script emits `{count, byFeasibility, proposals: [...]}` where each proposal carries `name, level, version, id, exportName, folder, file, pitch, behavior, trigger, feasibility, feasibilityDetail, settings, notes`. Use its computed `id`/`folder`/`file` verbatim — do not re-derive names. Write the worklist to a temp location or the module root; do not commit it.

### Step 2: Select targets and check collisions

1. Filter to the user's requested spells if any were named; otherwise take all.
2. For each target, check whether `scripts/automations/<folder>/` already exists:
   - Existing file **with** the `AUTO-GENERATED automation` banner → regeneration is allowed (overwrite).
   - Existing file **without** the banner → manually created; **never overwrite**. Drop it from the target list and report it as `skipped-manual`.
3. Read `scripts/automations/_index.js` and note existing ids to avoid id collisions with manual automations under different folder names.

### Step 3: Generate with parallel agents

Spawn one agent per spell with `model: opus`, up to **5 concurrently** (send a wave in a single message; start the next wave as results return). Each agent writes its own folder only, so parallel writes cannot conflict. Prompt template (embed the spell's proposal JSON — agents cannot see the conversation):

```
Implement a spell automation for the fantik-automations Foundry VTT module
(module root: <module root path>). First read, in this order:
- <skill-dir>/references/generation-conventions.md   (mandatory rules: autogenerated
  marker, degradation, style — follow them exactly)
- scripts/framework/registry.js      (definition shape contract, docblock at top)
- scripts/framework/triggers.js      (the ONLY events that exist and their contexts)
- scripts/framework/utils.js         (available helpers)
- scripts/automations/shadow-blade/shadowBlade.js    (exemplar: item lifecycle,
  concentration cleanup) and scripts/automations/gamblers-blade/gamblersBlade.js
  (exemplar: damage-card rewrite) — plus bladesong/darkness if the proposal
  resembles those patterns.

The proposal to implement:
<proposal JSON>

Write exactly one new file: <module root>/<proposal.file>
- Export a definition named <proposal.exportName> with id '<proposal.id>',
  version '1.0.0', autogenerated: true, and the banner comment
  (report: <report file>, date: <today>).
- Implement what existing events support; degrade the rest to marker effects
  (never chat reminder cards) per the conventions file. Never block the
  vanilla cast or roll.
- Do NOT edit _index.js, framework files, or any other automation.

Return ONLY a JSON object:
{
  "id": "...",
  "exportName": "...",
  "file": "relative path written",
  "status": "implemented" | "partial" | "marker-only",
  "degraded": ["parts that became marker effects or were left manual"],
  "settings": ["setting keys exposed"],
  "notes": "anything the user must know before trusting this code"
}
```

If an agent returns malformed output or fails, re-run that one spell; do not silently drop it.

### Step 4: Register and verify

After all agents finish (the orchestrator does this, never the agents):

1. Add one import line and one array entry per generated automation to `scripts/automations/_index.js`, matching its existing style.
2. Syntax-check every generated file and the index with a REAL ESM parse:
   `node --experimental-vm-modules "<skill-dir>/scripts/check_esm.mjs" <files...>`
   Do NOT use `node --check` — it parses `.js` files as CommonJS scripts and silently
   misses ESM-only syntax errors (e.g. `a ?? b && c`), which then crash in Foundry's
   browser loader. The check script parses without executing, so Foundry globals are fine.
3. On a syntax error, fix trivial issues directly or re-run that spell's agent with the error text.
4. Verify the count: generated + skipped-manual + failed must equal the target count.

### Step 5: Report

Tell the user:

- Totals: generated / skipped-manual / failed, and the status split (implemented vs. partial vs. marker-only).
- Per spell: one line with status and the degraded parts.
- What was NOT done: no Foundry runtime testing happened — the ESM check validates syntax only. The user must reload Foundry (automations register at init; new world settings `enabled-<id>` default to on) and test each spell at the table.
- How to audit later: `grep -rl "autogenerated: true" scripts/automations` lists generated automations; files without the banner are manual.

Do not commit anything. Do not delete or modify manual automations under any circumstances.

## Regeneration

Re-running the skill on the same report overwrites autogenerated files (fresh banner date) and refuses to touch adopted/manual ones. To adopt a generated automation as manual, the user removes the banner and the `autogenerated` flag — mention this when relevant.

## Additional Resources

### Reference Files

- **`references/generation-conventions.md`** — autogenerated marker format, overwrite policy, degradation rules (marker effects, never chat reminders), definition checklist, code style. Generator agents must read this before writing code.

### Scripts

- **`scripts/parse_proposals.mjs`** — parses a proposals report into a JSON worklist with precomputed ids, folders, and file paths (Node, no dependencies).
- **`scripts/check_esm.mjs`** — parse-only ES module syntax check (run with `--experimental-vm-modules`); the required replacement for `node --check`, which misses ESM-only syntax errors.
